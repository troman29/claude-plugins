# fork — ветка разговора в новом топике

**Цель.** `/fork [директива]` заводит новый топик и поднимает в нём сессию с историей текущего
разговора (`--resume <id> --fork-session`). Ветка живёт своей жизнью, донор не тронут.
Ключевой код: `handleOps` (ветка `cmd === 'fork'`), `spawnSession(mode='fork', forkFrom)`,
`buildLaunch`, `forkTopicTitle`, `deliverToFork`.

**Предусловия.** Форум-группа, бот с правом «Управление топиками», забинденный топик с
поднимавшейся хоть раз сессией (у биндинга есть `sessionId`).

**Юнитами уже закрыто** (`tests/core.test.ts`): разбор `/fork` и аргумента, состав команды
запуска (`--resume <донор> --fork-session`, каналы на месте, чужой `--continue` выкинут),
имя топика (суффикс + лимит 128).

## Позитив

### F1 — форк без директивы
- **Шаги.** В топике с живой сессией: `/fork`.
- **Ожидаемо.** Создан топик «<имя донора> ⑂»; в нём отбивка `⑂ Форкаю разговор` и команда с
  `--resume <донор> --fork-session`; в доноре — `⑂ Форкнул` со ссылкой на id топика;
  в `bindings.json` новый ключ с тем же `dir`; через ≤60 с у него появляется **свой** `sessionId`.
- **Fail-режим (корень).** `sessionId` ветки равен донорскому → потерян `--fork-session`, две
  сессии на один разговор затрут друг друга.
- **Смотреть.** `bindings.json`, hub-лог (`learned sessionId`), `tmux list-panes`, пейн ветки.

### F2 — форк с директивой
- **Шаги.** `/fork посчитай 2+2 и ответь числом`.
- **Ожидаемо.** Всё из F1 + директива доставлена **первым** сообщением ветки; ответ приходит
  в новый топик, а не в донора.
- **Fail-режим.** Директива ушла в неготовый пейн и потеряна (класс бага «первое сообщение при
  пробуждении») → в топике тишина. Корень: доставка без `waitPaneReady`.
- **Смотреть.** `screenlog.jsonl` (`tg_out` в новый thread), транскрипт сессии ветки.

### F3 — контекст донора виден в ветке
- **Шаги.** В доноре сказать факт («запомни: кодовое слово ПЛАТИНА»), затем `/fork что за кодовое слово?`.
- **Ожидаемо.** Ветка отвечает «ПЛАТИНА» — история дошла.
- **Fail-режим.** Ответ «не знаю» → форк стартовал с пустой историей (потерян `--resume`).

### F4 — донор не тронут
- **Шаги.** После F2 написать в донора обычное сообщение.
- **Ожидаемо.** Донор отвечает в своём топике; его `sessionId` в биндинге не изменился; пейн жив.
- **Fail-режим.** Донор молчит/умер → форк увёл его сессию (нет `--fork-session` либо убит пейн).

## Негатив и швы

### F5 — `/fork` вне топика (General/DM)
- **Ожидаемо.** `forkNeedsForum`, топик не создан, биндингов не прибавилось.

### F6 — форкать нечего
- **Шаги.** В свежем биндинге без `sessionId` — `/fork`.
- **Ожидаемо.** `forkNothingToFork`; топик не создан (иначе плодим пустые топики).

### F7 — не-админ
- **Ожидаемо.** Команда игнорируется молча, топик не создан.

### F10 — у бота нет права на топики
- **Шаги.** Снять «Управление топиками» → `/fork`.
- **Ожидаемо.** `forkTopicFailed` с текстом ошибки; биндинг НЕ создан (нет топика — нет ключа).

## Fault-injection

### F8 [СПЕЦ] — рестарт хаба между созданием топика и подхватом id
- **Шаги.** `/fork`, сразу `docker compose restart`/убить хаб; после подъёма — `/status` и
  сообщение в ветку.
- **Ожидаемо.** Биндинг ветки существует; если `sessionId` не успел записаться — он **пустой**,
  и следующий подъём стартует новую сессию, а не донорскую.
- **Fail-режим (корень).** В биндинге ветки лежит донорский id → `/restart` уводит ветку в
  чужой разговор. Поэтому биндинг пишется без `sessionId`, а не копией донорского.

### F9 [СПЕЦ] — два форка подряд
- **Шаги.** `/fork а` и сразу `/fork б` из одного топика.
- **Ожидаемо.** Два разных топика, два биндинга, два разных `sessionId`; директивы не перепутаны.
- **Fail-режим.** Один топик/один id → гонка на `loadBindings`/`saveBindings`.

**Найдено и починено по ходу (оба — не в самой команде, а в её соседях):**

1. **Рестарт ветки повторно форкал донора.** `/restart` берёт argv живого процесса, а там
   `--resume <донор> --fork-session` — перезапуск создавал ЕЩЁ один форк донора, теряя всё,
   что наработала ветка. Фикс: `relaunchCommand` при виде `--fork-session` резюмит собственный
   id ветки (guard-юниты в `core.test.ts`). Проверено живьём: после `/restart` в логе
   `--resume <id ветки>`, id в биндинге не изменился, ветка ответила «жив».
2. **Два форка подряд получали ОДИН `sessionId`.** `captureNewSessionId` угадывает разговор по
   свежему `jsonl` в папке — при параллельных стартах в одной папке оба видят один файл.
   Два биндинга на один разговор = перезапуск в чужую историю. Фикс двойной: чужой id не
   присваиваем (`sessionIdTaken`), а `syncSessionId` (хук говорит от имени самой сессии)
   стал авторитетным — забирает id у того, кто его угадал (`claimSessionId` + юниты).
   Проверено живьём: дубликатов в `bindings.json` не осталось, каждая ветка заявила свой id.
