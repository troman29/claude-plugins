# Feature: fork

**Цель.** `/fork [директива]` — ветка разговора в СВОЁМ топике: та же история до точки
разветвления, дальше живёт отдельно. Оригинальный топик и его сессия не трогаются.
Встроенный `/fork` у CLI отдаёт ветку фоновому агенту без интерфейса — поэтому команда
перехватывается хабом и до CLI не долетает.

**Код.** `parseOpsCommand` (`fork`), ветка `cmd === 'fork'` в `handleOps`, `forkTopicName`,
`buildLaunch(mode='fork')` → `--resume <id> --fork-session`, `spawnSession` (fresh для fork).

**Предусловие.** Контейнер, форум-группа, живая сессия с накопленным разговором,
у бота право «Управление темами».

---

## Позитив

**F1. Форк с директивой.**
- Шаги: в забинденном топике довести разговор до запоминаемого факта → `/fork <директива>`.
- Ожидаемо: создан топик «<имя> (fork)»; в нём «🌱 Ветка разговора» + запуск
  `--resume <id> --fork-session`; директива доезжает первым сообщением, агент по ней отвечает.
- Fail-режим: топик не создан (нет прав) / ветка стартует пустой (потерян `--resume`) /
  директива теряется (доставка до готовности пейна — корень тот же, что у `waitPaneReady`).
- Смотреть: API (топик+сообщения), `bindings.json` (новый ключ), `tmux list-panes`, пейн ветки.

**F2. Ветка помнит историю оригинала.**
- Шаги: в ветке спросить про факт, названный в оригинале ДО форка.
- Ожидаемо: помнит (история скопирована).
- Fail-режим: «не знаю» → форк стартовал как новая сессия.
- Смотреть: ответ в топике ветки.

**F3. Оригинал не затронут.**
- Шаги: после форка написать в исходный топик.
- Ожидаемо: отвечает та же сессия, её `sessionId` в `bindings.json` не изменился, пейн тот же.
- Fail-режим: `--resume` без `--fork-session` увёл бы оригинал в форк (классическая грабля).
- Смотреть: `bindings.json` до/после, `tmux list-panes`.

**F4. Ветка получает свой session id.**
- Шаги: после подъёма ветки посмотреть её биндинг.
- Ожидаемо: `sessionId` ветки ≠ `sessionId` оригинала (выучен через `captureNewSessionId`).
- Fail-режим: остался id оригинала → следующий подъём ветки поднимет/форкнет оригинал.
- Смотреть: `bindings.json`.

**F5. Форк без директивы.**
- Шаги: `/fork`.
- Ожидаемо: топик и ветка поднимаются, первого сообщения нет, ветка ждёт.
- Смотреть: пейн (пустая строка ввода), чат.

## Негатив / швы

**F6. `/fork` без разговора.** Топик забинден, но `sessionId` пуст → «Форкать нечего», топик не создаётся.

**F7. `/fork` в DM.** → «Ветке нужен свой топик», ничего не создаётся.

**F8. `/fork` без биндинга.** → «Тут нет привязки».

**F9. Нет права «Управление темами».** → понятная ошибка с подсказкой про право, биндинг не создан.

**F10. Команда не долетает до CLI.** `[ЭКСКЛЮЗИВ]`
- Шаги: `/fork привет` в топике.
- Ожидаемо: в пейне оригинала НЕ появляется набранный `/fork` (перехвачено хабом).
- Fail-режим: команда уходит встроенному CLI-форку → фоновый агент без интерфейса.
- Смотреть: пейн оригинала, `screenlog.jsonl`.

## Fault-injection `[СПЕЦ]`

**F11. Рестарт хаба сразу после создания топика.** Биндинг ветки уже в `bindings.json` →
после рестарта ветка жива/поднимается, дублей топиков нет.

**F12. Двойной `/fork` подряд.** Два топика-ветки, оба со своими id; оригинал цел.

**F13. Удаление топика-ветки.** `/delete` (или удаление топика) убирает биндинг и tmux ветки,
оригинал не затронут.
