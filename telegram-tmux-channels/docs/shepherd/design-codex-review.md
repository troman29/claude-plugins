# Жёсткое ревью PR shepherd

**Вердикт: в текущем виде запускать нельзя.** Архитектура хорошо разделяет Cyrus и хаб, но не гарантирует доставку. Она также допускает неверного владельца и опасное выполнение недоверенного текста.

Критический путь сейчас такой:

```text
GitHub → Cyrus → сокет → память хаба → очередь сессии → агент → GitHub
             200 OK       ↑ рестарт теряет состояние      ↓ новый webhook
                           └──────── петля и дубли ────────┘
```

## 1. Ошибки и пробелы архитектуры

### Блокеры запуска

1. **Нет сквозной гарантии доставки.** Cyrus получает ответ `accepted`, пока хаб ещё обрабатывает событие асинхронно. После этого GitHub уже не повторит доставку.
2. **Дедупликация может превратить временную ошибку в потерю.** План не говорит, когда Cyrus кладёт `delivery_id` в LRU. Если до ответа хаба, повтор после 503 будет отброшен.
3. **Запись ключа до отправки создаёт окно потери.** Хаб сохраняет ключ до отправки в pane. Падение между этими действиями оставит событие навсегда «обработанным».
4. **Таймеры живут только в памяти.** Рестарт теряет debounce CI, ревью и конфликтов. Крон повторяет только неуспешные HTTP-доставки, но GitHub уже получил 200.
5. **Нет долговечной входной очереди.** Нужны состояния `received`, `processing`, `delivered`, `dead`. Нужны атомарная запись, повтор и сверка после рестарта.
6. **Нет очереди ошибок.** Истечение шести часов, ошибка `gh`, ошибка spawn и исчерпание повторов не должны исчезать из журнала.
7. **Нет ограничения входной нагрузки.** Не определены размер очереди, параллелизм, лимит событий на PR и поведение при заполненном диске.
8. **Таймауты Cyrus не согласованы с HTTP webhook.** Три попытки сокета по пять секунд плюс backoff могут превысить таймаут GitHub. Это надо измерить в реальном обработчике.

### Владелец и гонки

1. **Эвристика не может выбирать владельца при неоднозначности.** Отправка в «лучший из N» опаснее пропуска. При двух кандидатах событие должно остановиться и запросить выбор.
2. **Липкий кэш не имеет срока владения.** Существование binding и папки не доказывает, что сессия ещё владеет PR.
3. **Нет операции передачи с compare-and-swap.** `/own`, закрытие, Mac-метка и повторный spawn могут одновременно изменить владельца.
4. **Два события могут создать два топика.** Нужна блокировка по `repo#PR` вокруг resolve, создания worktree, binding и первого сообщения.
5. **Повторное использование worktree опасно.** План не проверяет чистоту, текущего владельца, HEAD и работающий процесс.
6. **`git worktree add -B` может передвинуть локальную ветку.** Для чужой или активной ветки это недопустимо. Нужен новый worktree от точного SHA без сброса ссылки.
7. **MacBook не представлен в архитектуре.** Поэтому хаб примет отсутствие binding за отсутствие владельца и создаст конкурирующую сессию.
8. **Закрытый топик трактуется по-разному.** Архитектура создаёт новую сессию. UX требует открыть прежний топик и продолжить прежнюю сессию.
9. **Одна ветка может иметь несколько PR.** Кэш по PR и поиск по ветке должны запрещать неявное объединение таких PR.

### Петли и дубли

1. **Фильтр собственного sender не останавливает цикл CI.** Агент пушит исправление, новый CI падает, шеперд снова запускает агента.
2. **Лимит «три попытки» есть только в UX.** Архитектура не хранит номер попытки по PR, SHA и типу отказа.
3. **Фоновое наблюдение агента остаётся вторым диспетчером.** Фраза «если уже обработал» не устраняет одновременные push, rerun и ответы в ревью.
4. **Нужен один владелец автоматизации.** На время MVP шеперд должен заменить фоновый watcher либо работать только как уведомитель.
5. **Нужна причинная связь.** Каждое действие агента должно хранить исходное событие, SHA до действия и SHA результата.
6. **Нужен cooldown.** Повтор одного класса ошибки на новом SHA нельзя автоматически чинить бесконечно.
7. **Фильтр всех ботов может удалить CI.** У `check_suite` sender часто является ботом. Фильтр должен зависеть от типа события.

### Конфликт Ромы и события

1. **Нет единой последовательной почты сессии.** Сообщение Ромы и событие могут попасть в разные очереди и поменять порядок.
2. **Нет приоритетов.** Ручная остановка, смена решения и вопрос безопасности должны опережать CI и ревью.
3. **Нет отмены уже поставленного события.** `/esc`, `/own`, `/shepherd off` должны инвалидировать ожидающие события по версии владельца.
4. **Нет фиксации источника решения.** Журнал должен различать Рому, GitHub, watcher и автоматическое восстановление.
5. **Нет правила для активного хода.** Удержание до `Stop` может задержать срочное закрытие PR на шесть часов.

Рекомендуемая модель:

```text
входная очередь PR → сериализатор repo#PR → проверка владельца и версии
                                         ├─ ручное сообщение: высокий приоритет
                                         ├─ actionable-событие: обычный приоритет
                                         └─ info: только состояние
```

### Безопасность

1. **`author_association` не защищает от prompt injection.** Участник организации может ошибиться, быть взломан или вставить чужой текст.
2. **Недоверенными являются не только комментарии.** К ним относятся CI-логи, title, body, branch, commit message, имя job, diff и имена файлов.
3. **Обрамление словами «это данные» не является границей безопасности.** Агент всё равно читает текст как часть одного промпта.
4. **В MVP нельзя инжектировать CI-логи.** Агент должен получить идентификатор проверки и сам запросить нужный фрагмент.
5. **Маскирование несколькими regex недостаточно.** Оно не знает внутренние токены, приватные ключи, cookies и новые форматы секретов.
6. **Нельзя писать сырой payload в журналы.** Журнал должен хранить идентификаторы, решение, хэши и безопасное резюме.
7. **Сокет `0600` не создаёт границу между агентом и хабом.** Агент работает тем же Unix-пользователем и может вызвать `spawn`, `send` или `pr-event`.
8. **Нужен отдельный пользователь сервиса или отдельный сокет.** Для Cyrus оставьте только команду приёма события. Административные команды держите отдельно.
9. **Схема входного JSON не определена.** Нужна строгая проверка типов, размера, enum, URL, repo и недопустимых полей.
10. **PAT `thomas5788` имеет слишком широкие права.** Чтение событий и запись в PR надо разделить. Автоматические записи включайте отдельным этапом.
11. **Автоматический код работает с bypass-разрешениями.** Поэтому комментарий или лог фактически может инициировать push и внешние действия.
12. **Удаление IP allowlist допустимо только после проверки HMAC на точном raw body.** Нужны лимит тела, rate limit, только POST и метрика неверных подписей.

### Корректность событий

1. **Успешный `check_suite` отбрасывается.** Тогда карточка не узнает о зелёном CI, а автомерж не получит сигнал.
2. **Approval не будит и почти не обрабатывается.** Это противоречит цели убрать ручное «смержил» в репозиториях без автомержа.
3. **`check_suite.pull_requests` может быть пуст или содержать несколько PR.** Поиск по SHA должен обрабатывать ноль, один и несколько результатов.
4. **`mergeStateStatus=DIRTY` не всегда означает только текстовый конфликт.** Нельзя без проверки приравнивать все `DIRTY` к конфликту.
5. **Проверка конфликтов каждые 30 минут создаёт лишнюю сложность для редкого события.** Для MVP достаточно ручной проверки после push в базу или по запросу.
6. **Крон редоставки смотрит только последние 100 событий.** При всплеске часть ошибок может выпасть из окна.
7. **Не определён источник истины для результата доставки.** ACK сокета, ACK stub и появление delivery id в transcript означают разные уровни.
8. **Нет политики хранения.** Нужны сроки для событий, владельцев, аудита, ошибок и данных PR.

## 2. Противоречия architecture.md и ux.md

1. **Владелец:** архитектура выбирает ветку и эвристику; UX требует реестр, хук и метку. Выбрать явный реестр с версией. Ветку использовать только для предложения владельца.
2. **Mac:** архитектура автоматически спавнит; UX запрещает спавн при Mac-метке. Выбрать запрет. Иначе две сессии пушат в одну ветку.
3. **Закрытый топик:** архитектура спавнит новый; UX открывает прежний. Выбрать прежний топик, если сохранены binding и session id.
4. **Merged:** архитектура будит unloaded-сессию; UX называет merge тихим и местами запрещает будить. Выбрать per-repo политику. Для console/dev будить владельца из-за post-merge работ.
5. **CI green:** архитектура дропает; UX обновляет карточку и включает автомерж. Выбрать обработку без инжекта агенту.
6. **Approval:** архитектура доставляет только живой сессии; UX использует approval для автомержа. Выбрать обновление состояния без пробуждения.
7. **Агрегация:** архитектура использует разные окна 30 и 45 секунд; UX заявляет единое окно 60 секунд. Выбрать одно окно 60 секунд.
8. **Место агрегации:** схема UX приписывает склейку Cyrus; архитектура помещает её в хаб. Выбрать хаб. Только хаб знает состояние PR.
9. **Ответы в GitHub:** архитектура запрещает Cyrus писать; UX требует комментарий, ярлыки, ответы и закрытие тредов. Оставить запись в GitHub за агентом. Липкий комментарий и ярлыки отложить.
10. **Автоспавн:** архитектура спавнит любой actionable PR разрешённого автора; UX вводит Mac-метку, лимит три и очередь. В MVP автоспавн запретить полностью.
11. **Объём P0:** UX включает карточки, stall detector, edited messages, локаль и автомерж. Эти функции не нужны для проверки маршрутизации. Перенести их после надёжной доставки.
12. **Терминальная цель:** architecture.md проектирует PR-маршрутизатор; ux.md проектирует новую операционную систему хаба. Это два проекта. Выпускать их одним релизом нельзя.

## 3. Что резать и без чего запускать нельзя

### Убрать из первого запуска

1. Автоспавн топиков и worktree.
2. Автоматическое исправление CI и конфликтов.
3. Автомерж, закрытие issue и напоминания ревьюерам.
4. CI-логи внутри промпта.
5. Карточки, переименование топиков и кнопки.
6. Детектор тишины, `/compact` и независимый сторож.
7. Обработку `edited_message`.
8. Ленту, дайджест, ярлыки и липкий комментарий GitHub.
9. Поиск конфликтов по таймеру.
10. Общие `list`, `send` и `spawn` на сокете Cyrus.
11. Обновление upstream Cyrus в том же изменении.

### Обязательно до первого инжекта

1. Долговечная очередь с повтором после рестарта.
2. Строгая схема нормализованного события.
3. Явная привязка `repo#PR → topic` с версией владельца.
4. Запрет доставки при нуле или нескольких владельцах.
5. Сериализация обработки по `repo#PR`.
6. Отдельная команда и право сокета только для событий Cyrus.
7. Дедупликация с состоянием, а не одним булевым ключом.
8. Очередь ошибок и служебный сигнал о каждом необработанном событии.
9. Фильтр собственных действий по типу события.
10. Запрет сырых CI-логов и недоверенных команд в промпте.
11. Shadow-режим без инжекта и без записи в GitHub.
12. Метрики `received`, `persisted`, `routed`, `delivered`, `failed`, `lag`.

### Этапы

1. **MVP-0: наблюдение.** Один sandbox-репозиторий, отдельное приложение, приём событий, HMAC, долговечная очередь и журнал решений. Готово, когда 100 тестовых событий переживают три рестарта без потерь и дублей.
2. **MVP-1: безопасная доставка.** Только CI failure, changes requested и merged. Только явно привязанная живая или unloaded-сессия. Готово, когда каждое событие появляется ровно один раз в правильном transcript.
3. **MVP-2: боевой shadow.** Один реальный репозиторий. Шеперд вычисляет маршрут, но не инжектирует. Готово после семи дней без неверного владельца и необъяснимых расхождений.
4. **MVP-3: уведомитель.** Инжект содержит факты и ссылки, но не команду исправлять или пушить. Готово после двадцати событий без дублей, потерь и конфликтов с Ромой.
5. **v1: исполнитель.** Добавить лимиты попыток, причинную связь, ручной приоритет и безопасные автоматические действия. Автоспавн оставить выключенным до отдельной приёмки Mac-владения.
6. **v1.1: UX хаба.** Карточки, состояния топика, edited messages, stall detector и дайджест выпускать независимо от маршрутизатора.

## 4. План тестирования: чего не хватает

1. **Отдельная среда обязательна.** Нужны отдельные GitHub App, Telegram bot, группа, Unix-пользователь, state dir и контейнер или VM.
2. **Нельзя запускать dev-хаб на живом tmux.** Имя `agents` и launcher-ссылки глобальны. Docker-харнес должен доказать изоляцию до теста webhook.
3. **Нужны crash-тесты на каждой границе.** Убить процесс после HMAC, записи события, ACK, resolve, постановки в очередь и отправки в pane.
4. **Нужны тесты заполненного диска и повреждённого state.** Система должна вернуть ошибку до HTTP 200 и не потерять событие.
5. **Нужны гонки.** Два webhook одного PR, redelivery, сообщение Ромы, `/own`, закрытие топика и рестарт должны идти одновременно.
6. **Нужны тесты неверного владельца.** Два топика одной папки, одинаковые ветки в разных repo, закрытый binding, stale session id и Mac-метка.
7. **Нужны тесты безопасности.** Команды в комментарии, ANSI, HTML, нулевые байты, огромный payload, секреты и инструкции в CI-логе.
8. **Нужен тест прав сокета.** Процесс агента не должен вызывать административные команды хаба.
9. **Нужен контрактный тест реальных payload.** Сохранить payload каждого события из sandbox и сравнить с типами нормализации.
10. **Нужен тест нескольких PR на SHA.** Система должна остановиться при неоднозначности.
11. **Нужен тест GitHub rate limit и 403.** Событие остаётся в очереди, а причина видна оператору.
12. **Нужен тест Telegram rate limit и ошибки редактирования.** Это важно до карточек и переименований.
13. **Нужен тест лимита памяти.** Очередь и логи должны обрабатываться потоково и иметь жёсткий размер.
14. **Нужна сверка на другом конце.** Успех означает delivery id в transcript нужной сессии, а не строку `forwarded` в Cyrus.
15. **Нужна безопасная боевая проверка.** Сначала prod payload → shadow-таблица. Потом оператор вручную сравнивает маршрут с живым топиком.
16. **Нужен rollback-тест.** Отключение флага не должно терять накопленные события или запускать старый Cyrus-путь неожиданно.
