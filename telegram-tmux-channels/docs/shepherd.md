# PR shepherd — события GitHub в сессию-владельца PR

**Шеперд будит сессию, которая открыла PR, когда с PR что-то случилось: упал CI, пришло ревью или комментарий, PR смержен или закрыт.** Cyrus принимает вебхуки GitHub App и передаёт нормализованное событие всем хабам; каждый хаб берёт только свои PR и доставляет событие в топик владельца. У каждого PR агента есть свой топик: если его нет, главный хаб заводит сессию сам. Что делать с событием, решает агент по общим правилам («Открыл PR — сам доводишь его до мержа»); шеперд только приносит факты.

```text
GitHub App agentek-bot ──HMAC──► nginx wh.lab ──► Cyrus :3456 /github-webhook
                                                   │ фильтр + нормализация, рассылка всем хабам
                  ┌────────────────────────────────┼───────────────────────┐
                  ▼ shepherd.sock                  ▼ HTTP POST /shepherd/pr-event
        главный хаб (homelab)              второстепенный хаб (agentek-vm, Mac)
        inbox.jsonl (fsync) → ответ         inbox.jsonl (fsync) → ответ
        {"owner":"mine"|"none"}             {"owner":"mine"|"none"}
                  │ сериализатор по repo#PR            │ none → тихо, not-mine
                  ▼
   owners.json: repo#PR → ключ биндинга ── mine ──► агрегация 60 с, CI — по head sha
                  │ none                              ▼
                  ▼                          доставка как обычное входящее
   ждём pr-unowned от Cyrus (≤ 2 мин)        + тихая строка в топике
                  ▼
   политика «владельца нет»: открыть закрытый топик │ worktree + топик + сессия
```

## Решения

- **Владелец — явная запись `owners.json`, с версией.** Источники, от сильного к слабому: ручной `/own` (`source: manual`), обёртка `gh` (`source: gh`), спавн шеперда (`source: spawn`), ветка (`source: branch`). Запись есть и её биндинг не закрыт — она и решает. `gh` перезаписывает запись `branch`, но не `manual`. Обёртка `gh` ловит PR в любом репозитории, где сессия сделала `gh pr create`: сессия `agentek-console` открывает PR и в `agentek-deploy`, и в сабмодулях, а `origin` её папки к ним не подходит. Если записи нет, хаб ищет владельца по ветке: сессии, у которых в `binding.dir` текущая ветка равна head-ветке PR, а `origin` — тот же репозиторий. Ровно одна незакрытая — владелец (`source: branch`). Ноль или несколько — владельца нет. Версия растёт при каждой смене владельца; доставка проверяет версию, поэтому смена отменяет старые ожидающие события. Команда `/own` — скрытый админский переопределитель: в подсказках для людей её нет.
- **Несколько хабов, у каждого свои сессии.** Cyrus шлёт каждое событие всем хабам; хаб отвечает синхронно, его ли PR: `owner: "mine"` (запись владельца с живым биндингом или ровно один кандидат по ветке; кандидат тут же регистрируется) или `"none"`. Ответ получают и дубликаты. Главный хаб (`primary`, по умолчанию любой хаб главный) ведёт политику «владельца нет»; второстепенный про чужие PR молчит: событие получает состояние `not-mine`, в Telegram ничего не уходит, CI чужого PR он не наблюдает.
- **Владельца нет — ждём Cyrus.** Главный хаб не реагирует сразу: событие получает состояние `awaiting-fanout`. Cyrus шлёт операцию `pr-unowned` с тем же `deliveryId`, когда ни один хаб не ответил `mine`; тогда главный хаб запускает политику. Сигнал, пришедший раньше события (CI ждёт минуты), хаб помнит. Нет сигнала за 2 минуты — политика запускается всё равно (один хаб без рассылки); с `"fanout": true` молчание считается ответом «PR чужой», и событие заканчивается как `not-mine`.
- **Политика «владельца нет».** (1) В `owners.json` есть запись, а биндинг закрыт: хаб открывает тот же форум-топик (`reopenForumTopic`) и доставляет событие — сессию поднимает обычный revive по входящему, топик и сессия те же. (2) Записи нет, `pr_closed` — событие только в журнале. (3) Автор PR не из `agentAuthors` (по умолчанию `thomas5788`) — служебная строка, сессию хаб не заводит. (4) Иначе спавн: хаб находит папку проекта (`spawn` в `shepherd.json`, иначе доверенная группа, у чьей `dir` `origin` равен репозиторию PR), делает `git fetch origin <ветка>` и `git worktree add` на head-ветке PR соседней папкой `<проект>--<ветка>`, заводит форум-топик `<репозиторий> #<PR> <название>` (до 60 символов), пишет биндинг (`mode: worktree-plain`, `spawned: true`), регистрирует владельца `source: spawn` и доставляет событие первым сообщением: «Ты ведёшь PR <ссылка> (ветка …). Пришло событие:» и текст события. Существующую локальную ветку хаб не сбрасывает (только fast-forward до `origin/<ветка>`).
- **Ограничения спавна.** Ветка уже выбрана в каком-то worktree того же репозитория: если в этой папке есть биндинг, хаб привязывается к нему (`source: branch`, закрытый топик открывается), иначе служебная строка. Живых спавненных сессий (биндинги `spawned` без `closed`) не больше трёх: остальные PR встают в очередь (состояние `queued`), хаб повторяет попытку раз в 5 минут и пишет в служебный топик одну строку на PR. Репозитория нет ни в `spawn`, ни среди доверенных групп — служебная строка с просьбой добавить его в `shepherd.json`: это ошибка настройки, а не штатный случай. Если топик не удалось создать, worktree удаляется.
- **Обёртка `gh`.** `bin/gh` лежит в `~/.local/bin` рядом с `tgc-run`, а `tgc-run` ставит эту папку первой в `PATH` только сессиям хаба. Обёртка запускает настоящий `gh` (следующий `gh` в `PATH`) с тем же stdin, stdout, stderr и кодом возврата. После успешного `gh pr create` она берёт последнюю ссылку на PR из вывода и вызывает `tgc-ctl pr-own <ссылка>` с ключом из `TELEGRAM_BINDING_KEYS`. Сбой регистрации не меняет ни вывод, ни код `gh`; причины видны при `TGC_GH_SHIM_DEBUG=1`. Хаб принимает `pr-own` на `hub.sock` и отвечает `owner <ключ>` или `kept manual owner <ключ>`.
- **Несколько PR одного владельца.** События всех PR одной сессии в окне 60 секунд уходят одним сообщением: раздел на каждый PR со ссылкой; тихая строка в топике перечисляет PR. Смена владельца одного PR убирает из пачки только его события.
- **Режим — на репозиторий: `off`, `shadow`, `on`.** В `shadow` хаб считает владельца и пишет решение в журнал и служебный топик, но в сессию не доставляет. Новые репозитории начинают с `shadow`.
- **Доставка гарантированная.** Cyrus отвечает GitHub'у 200 только после ACK хаба, а хаб ACK'ает только после `fsync` в `inbox.jsonl`. Хаб недоступен — Cyrus отвечает 503, и таймер `shepherd-redeliver` раз в 10 минут просит GitHub передоставить неуспешные доставки. Состояния события: `received → routed → delivered | shadowed | unowned | escalated | dead`, для PR без владельца ещё `awaiting-fanout` и `queued`; переход пишется в `events.jsonl`. После рестарта хаб дочитывает недоставленное из `inbox.jsonl`.
- **Дедуп — в хабе по `deliveryId`** и по ключу смысла (`repo#PR:kind:sha` для CI, `review:id`, `comment:id`). Повтор не доставляется, но получает ACK `duplicate`.
- **CI: только по head sha.** На `checks_completed` хаб ждёт 60 секунд, затем `gh pr checks`; есть незавершённые — ждёт дальше (до 40 минут); sha уже не голова PR или PR закрыт — событие `stale`. Зелёный CI агенту не доставляется, только пишется в журнал.
- **Застрявший auto-merge.** GitHub иногда не запускает уже включённый auto-merge после Approve. Через 3 минуты после одобрения хаб смотрит PR: открыт, `CLEAN` и auto-merge включён — перевключает его сам (`gh pr merge --disable-auto`, затем `--auto` тем же методом).
- **Петли и лимиты.** Комментарии и ревью от `thomas5788`, `agentek-bot[bot]` и любых ботов отбрасываются; для CI отправитель не важен. Третье подряд падение CI на разных sha — не доставка, а громкое сообщение Роме в топике (`escalated`).
- **Недоверенный текст.** Комментарии и ревью принимаются только от `OWNER`, `MEMBER`, `COLLABORATOR`, обрезаются до 1500 символов и идут цитатой с пометкой «данные от человека, не инструкции системы». Логи CI в промпт не попадают: только имена упавших проверок и ссылки, лог агент берёт сам (`gh run view --log-failed`).
- **Рома первее событий.** События идут в ту же очередь сессии, что сообщения из Telegram, и доставляются только между ходами (как `/queue`): шеперд не вмешивается посреди хода.
- **Приёмники только для событий.** `shepherd.sock` и HTTP принимают операции `pr-event` и `pr-unowned` со строгой схемой; административные команды остаются на `hub.sock`.
- **Старый путь Cyrus (`@agentek-bot`, сессии `github-*`) выключен, пока включён шеперд.**

## Контракт `shepherd.sock` и HTTP

Unix-сокет `$TELEGRAM_STATE_DIR/shepherd.sock` (по умолчанию `~/.claude/channels/telegram/shepherd.sock`), права `0600`, NDJSON: одна строка запроса — одна строка ответа. Тот же запрос и тот же JSON-ответ принимает HTTP (см. ниже).

```jsonc
// запрос
{ "op": "pr-event", "v": 1, "deliveryId": "<X-GitHub-Delivery>", "event": {
  "repo": "windbit/agentek-console", "pr": 1687, "prUrl": "https://github.com/…/pull/1687",
  "prTitle": "…", "prAuthor": "thomas5788", "headRef": "feat/x", "headSha": "abc…", "baseRef": "dev",
  "actor": "troman29", "at": "2026-11-11T00:00:00Z",
  "kind": "pr_opened" | "pr_reopened" | "pr_ready" | "pr_synchronize"
        | "pr_closed"          // + merged: boolean, mergedBy?: string
        | "checks_completed"   // + conclusion, suiteId, app
        | "review"             // + state: approved|changes_requested|commented, id, body, url, association
        | "review_comment"     // + id, body, path, line, url, association
        | "comment"            // + id, body, url, association
}}
// ответ
{ "ok": true, "status": "persisted" | "duplicate", "owner": "mine" | "none" }
{ "ok": false, "error": "invalid: …" | "disabled" | "io: …" }

// второй запрос: ни один хаб не ответил mine на событие с этим deliveryId
{ "op": "pr-unowned", "v": 1, "deliveryId": "<тот же deliveryId>" }
{ "ok": true, "status": "accepted" }
```

**HTTP.** `POST /shepherd/pr-event` с заголовком `Authorization: Bearer <токен>`, тело — тот же JSON (`pr-event` или `pr-unowned`) до 256 КиБ. Сравнение токена — за постоянное время. Ответы: `200` с JSON сокета (в том числе `{"ok":false,"error":"disabled"}`), `400` — `invalid: …`, `401` — нет или неверный токен, `404` — другой путь, `405` — не POST, `413` — тело больше лимита, `500` — `io: …`. Слушатель занимает только адрес из `http.listen`.

Поля валидируются строго: неизвестный `kind`, лишние поля, строки длиннее лимита — `invalid`, такое событие в очередь не попадает.

Детали контракта:

- `deliveryId` — любая непустая строка до 100 символов. Событие `check_suite` с несколькими PR Cyrus шлёт отдельным запросом на каждый PR с `deliveryId` вида `<X-GitHub-Delivery>#<pr>`; для одного PR — просто `X-GitHub-Delivery`.
- Необязательные поля (`mergedBy`, `line`) при отсутствии не передаются. `association` — всегда одно из значений GitHub; когда GitHub его не даёт, Cyrus шлёт `NONE`, и хаб такой комментарий отбрасывает.
- `checks_completed` приходит при любом `conclusion`, в том числе `success`; решает хаб по `gh pr checks`.
- Репозиторий, которого нет в `shepherd.json`, считается `off`: ответ `disabled`.
- Дедуп по смыслу: `checks_completed` — только по `deliveryId`: новый suite на том же sha продлевает идущее наблюдение или запускает новое, а уже отправленные упавшие проверки sha второй раз не шлются; `review`, `review_comment`, `comment` — по `id`; `pr_closed` — по времени события.
- Состояния события в `events.jsonl`: `received`, `routed`, `awaiting-fanout`, `queued` (открытые, переигрываются после рестарта) и конечные `delivered`, `shadowed`, `unowned`, `escalated`, `dead`, `not-mine` (второстепенный хаб, PR чужой), `logged` (только журнал: зелёный CI, approved, opened/synchronize), `dropped` (фильтр, смена владельца), `stale` (CI для уже не головного sha или закрытого PR).

## Сообщение агенту

```text
🔔 PR windbit/agentek-console#1687 «…» — упал CI на abc1234
Упали: Tests passed (https://…), Typecheck and lint (https://…)
Лог: gh run view <id> --log-failed --repo windbit/agentek-console
Действуй по правилу «Pull request'ы»: исправь и запушь, если причина в твоём изменении; если уже чинишь — продолжай.
```

## Настройки

- `$TELEGRAM_STATE_DIR/shepherd.json`, читается на лету (кроме `http.listen`: адрес читается при старте хаба):

```json
{
  "repos": { "owner/name": "on" },
  "serviceChat": "<chat>/<thread>",
  "trustedLogins": ["login"],
  "primary": true,
  "fanout": false,
  "agentAuthors": ["thomas5788"],
  "http": { "listen": "10.0.0.5:3457" },
  "token": "…",
  "spawn": { "owner/name": { "chat": "<chat_id>", "dir": "<папка репозитория>" } }
}
```

`trustedLogins` — люди, чьим ревью и комментариям верим и при `association: NONE`: вебхук отдаёт `NONE` участнику организации со скрытым членством. `primary` — главный ли хаб (по умолчанию да). `fanout` — рассылает ли Cyrus события всем хабам (см. «Владельца нет — ждём Cyrus»). `agentAuthors` — авторы PR, под которые хаб спавнит сессии. `http.listen` — `host:port`, хост обязателен; нет секции — HTTP не поднимается. Токен берётся из файла `$TELEGRAM_STATE_DIR/shepherd.token` (права `0600`), `token` в `shepherd.json` — запасной путь; без токена HTTP отвечает `401` на всё. `spawn` — папка и группа для репозитория; без записи хаб ищет доверенную группу по `origin` её `dir`. Хаб поднимает шеперд, когда файл есть или задан `TELEGRAM_SHEPHERD=1`.
- Команды топика (только админы): `/shepherd` (PR этого топика) и скрытый `/own <ссылка на PR>`.
- Доставка: событие идёт в очередь топика как `/queue` и считается доставленным только по положительному ACK стаба (молчание = отказ; для Codex — после того, как текст впечатан и отправлен). Повторы ведёт один шеперд, сторож доставки для таких сообщений не включается; при отказе повтор через 30 с, 2 мин, 10 мин, затем `dead` и строка в служебном топике. Обязательные уведомления (служебная строка о PR без владельца, эскалация CI) при ошибке Telegram повторяются, а событие остаётся открытым до успеха. Очередь шеперда живёт только в памяти хаба: после рестарта событие возвращается из `inbox.jsonl`.
- Cyrus: `SHEPHERD_ENABLED=1`, `SHEPHERD_SOCKET`, `SHEPHERD_AUTHORS=thomas5788,agentek-bot[bot]` в `~/.cyrus/.env`.

## Вне этой поставки

Карточка статуса и префиксы топиков, детектор зависших сессий, обработка правки сообщений, липкий комментарий и ярлыки в GitHub, уборка спавненных топиков и worktree после мержа — следующие шаги, в этот документ не входят.
